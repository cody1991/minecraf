# Research: 生物、植物与天气系统

**Feature**: 008-biome-weather-system  
**Date**: 2025-12-12

## 1. 动物渲染方案

### Decision
使用 Three.js BoxGeometry 组合构建简化的方块风格动物模型（Minecraft 风格），每种动物由多个立方体组成（身体、头、腿等）。

### Rationale
- 与游戏整体方块美学一致
- 无需外部 3D 模型文件，减少加载时间
- 易于程序化生成和动画控制
- 性能友好，可使用 InstancedMesh 优化同类动物渲染

### Alternatives Considered
1. **GLTF 模型加载**: 需要额外资源文件，增加复杂度
2. **Sprite 2D 贴图**: 不符合 3D 游戏风格
3. **复杂多边形模型**: 性能开销大，与方块风格不匹配

## 2. 动物 AI 行为系统

### Decision
采用有限状态机（FSM）实现动物 AI，状态包括：Idle（静止）、Wandering（漫游）、Fleeing（逃跑）。

### Rationale
- FSM 简单直观，易于调试和扩展
- 满足规格中"随机移动、停留、逃跑"的需求
- 低计算开销，适合大量动物同时运行

### Alternatives Considered
1. **行为树（Behavior Tree）**: 过于复杂，当前需求不需要
2. **GOAP（目标导向行动规划）**: 过度设计
3. **纯随机移动**: 行为不够自然

### State Definitions
```
Idle: 原地静止 2-5 秒，偶尔播放"吃草"动画
Wandering: 随机选择方向，移动 3-8 秒
Fleeing: 检测到玩家靠近（< 5 格），快速远离
```

## 3. 植物生成策略

### Decision
在地形生成阶段（TerrainGenerator）后，由 PlantGenerator 根据生物群系类型在表面方块上放置植物。植物作为特殊方块类型存储在区块数据中。

### Rationale
- 与现有区块系统无缝集成
- 植物跟随区块加载/卸载，无需额外管理
- 可利用现有的 ChunkMesh 渲染管线

### Alternatives Considered
1. **独立实体系统管理植物**: 增加复杂度，植物不需要 AI
2. **装饰层叠加**: 需要额外渲染通道
3. **后处理生成**: 可能导致区块边界不一致

### Biome-Plant Mapping
```
Plains: 花朵(40%), 高草(50%), 蘑菇(10%)
Lake: 无植物
Mountain: 高草(30%), 枯灌木(20%), 无(50%)
Desert: 仙人掌(15%), 枯灌木(25%), 无(60%)
```

## 4. 天空渲染方案

### Decision
使用 Three.js ShaderMaterial 创建动态天空球（Skydome），通过 uniform 传入时间参数控制颜色渐变。太阳和月亮使用带纹理的平面（PlaneGeometry）固定在天空球内侧。

### Rationale
- 着色器控制颜色渐变性能最优
- 天空球确保任何视角都有天空背景
- 太阳/月亮作为独立对象便于位置计算

### Alternatives Considered
1. **CubeMap 天空盒**: 静态，无法实现动态昼夜变化
2. **多层渐变平面**: 边缘可见接缝
3. **后处理着色器**: 增加渲染复杂度

### Sky Color Timeline
```
时间(游戏刻)    颜色
0 (午夜)       #0a0a2e (深蓝)
6000 (日出)    #ff7e47 (橙红)
12000 (正午)   #87ceeb (天蓝)
18000 (日落)   #ff6b35 (橙红)
24000 (午夜)   #0a0a2e (深蓝)
```

## 5. 雨滴粒子系统

### Decision
使用 Three.js Points（粒子系统）渲染雨滴，粒子在玩家周围一定范围内生成，持续下落并循环重置。

### Rationale
- Points 是 Three.js 中最高效的大量小对象渲染方式
- 可通过着色器控制粒子运动，减少 CPU 开销
- 易于控制粒子密度和范围

### Alternatives Considered
1. **Instanced 细长立方体**: 性能不如粒子系统
2. **Sprite 雨滴**: 面向相机开销大
3. **后处理雨滴效果**: 不够立体

### Parameters
```
粒子数量: 5000-10000
生成范围: 玩家周围 32x32x64 区域
下落速度: 15-20 单位/秒
粒子大小: 0.05-0.1 单位
```

## 6. 游戏时间系统

### Decision
创建独立的 TimeSystem 类管理游戏时间，1 个游戏日 = 24000 游戏刻 = 20 分钟现实时间。

### Rationale
- 与 Minecraft 原版时间系统一致，玩家熟悉
- 独立模块便于其他系统订阅时间变化
- 可扩展支持时间加速/暂停功能

### Time Calculation
```
1 游戏刻 = 50ms 现实时间
1 游戏日 = 24000 刻 = 1200 秒 = 20 分钟
日出: 0-2000 刻
白天: 2000-10000 刻
日落: 10000-12000 刻
夜晚: 12000-24000 刻
```

## 7. 动物生成与管理

### Decision
EntityManager 在区块加载时检查是否需要生成动物，每区块最多 4 只，生成概率基于生物群系类型。动物数据不持久化，区块卸载时销毁。

### Rationale
- 符合规格中"每区块最多 4 只"的限制
- 简化实现，无需序列化动物状态
- 跟随区块生命周期，内存管理简单

### Spawn Rules
```
Plains: 80% 概率生成 1-4 只动物
  - 牛 30%, 羊 30%, 猪 25%, 鸡 15%
Lake: 不生成动物
Mountain: 20% 概率生成 1-2 只动物
  - 羊 70%, 鸡 30%
```

## 8. 性能优化策略

### Decision
采用以下优化措施确保 50 只动物场景 30+ FPS：
1. 动物 LOD：远距离简化模型
2. 视锥剔除：不渲染视野外动物
3. AI 更新节流：远距离动物降低 AI 更新频率
4. 雨滴粒子 GPU 计算：使用着色器更新位置

### Rationale
- 多层次优化确保各场景流畅
- 优先优化影响最大的部分（渲染和 AI）
- 利用 GPU 减轻 CPU 负担

### LOD Distances
```
近距离 (< 16 格): 完整模型 + 动画
中距离 (16-32 格): 简化模型 + 降频动画
远距离 (> 32 格): 最简模型 + 无动画
超远距离 (> 64 格): 不渲染
```
